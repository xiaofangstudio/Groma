# 渲染性能优化（第一轮 + 2026-11-23 缩略图补丁 + 2026-11-26 多画板索引）

日期：2026-11-22 ｜ 补丁：2026-11-23、2026-11-26
范围：画布绘制、平移、高 DPI、图层树首屏、页缩略图、多画板可见区。目标不是“跑分好看”，而是拖拽、平移、缩放时先不卡。

## 这一轮改了什么

### 1. 交互时降级细节

`src/render/draw.ts` 增加 `DrawOptions`：

- 拖动、缩放、画新对象时 `interactive=true`。
- 交互中跳过画板阴影、画板名称标签和点阵网格。
- 松手后自动回到完整细节，不需要手动刷新。

画板阴影每帧 `shadowBlur=18`，是 Canvas 2D 最贵的绘制之一。交互时先把它拿掉，松手再补回来。

### 2. 画布像素预算

`src/ui/CanvasView.tsx` 的 `pickDpr()`：

```text
dpr = min(系统 DPR, 2, sqrt(8,000,000 / (宽 × 高)))
```

- 最多 800 万物理像素，避免 4K / 150% 缩放下 canvas 缓冲区过大。
- DPR 上限 2，超过 2 的收益远小于显存与填充成本。
- 2D 上下文改为 `{ alpha:false, desynchronized:true }`，减少合成与同步开销。

### 3. 平移用快照缓存

旧逻辑：每个 `pointermove` 都把整个场景重画一遍。
新逻辑：

- 按下平移时，把画布内容区裁成一张位图缓存。
- 移动时只把缓存位图按位移画回去，再重画标尺。
- 用 `requestAnimationFrame` 合并同一帧内的多次移动。
- 松手时才把最终 viewport 一次性写回 store。
- 平移中忽略滚轮，避免和缩放打架。

缓存只在平移期间存在，结束或取消立即释放。

### 4. 移除常驻模糊

`.canvas-tip` 原来的 `backdrop-filter: blur(4px)` 会一直让 GPU 合成一层模糊。已改成不透明度更高的纯色底，画布上方不再常驻模糊层。

### 5. 滚轮缩放合并到帧

旧逻辑：每个 `wheel` 事件立即提交一次 zoom，并触发一次全场景重绘。
新逻辑：

- `wheel` 事件只累积 `deltaY`，同一帧内最多提交一次缩放。
- 缩放期间进入低细节模式，停手 180ms 后恢复画板阴影、名称标签与点阵网格。
- 平移进行中忽略滚轮，避免平移和缩放打架。

### 6. 图层树默认折叠

旧图层面板会把整棵树一次性铺开：5000 个节点就是 5000 行 React。
现在：

- 每行有展开 / 折叠箭头，默认只画顶层画板。
- 选中画布里的深层节点时，自动展开它到当前页面的那一条路径。
- 叶子节点不显示空箭头，缩进按层数计算。

这一刀不是为了“好看”，是为了打开大工程时左栏不先卡死。

## 第二轮：页缩略图不再和主画布抢帧（2026-11-23）

用户观察到的“只该画一个地方，但基本同时画”发生在页缩略图：

- 旧实现：`PageThumbnail` 在 React 提交阶段同步调用 `drawPageThumbnail`，而且每次 `doc` 变化都把整页所有后代节点重画一遍；主画布则在下一帧 `requestAnimationFrame` 绘制。两者会挤在同一帧，复杂页面还会让缩略图单独做一遍整页遍历。
- 新实现：当前页缩略图改为 100ms 尾部合并，连续拖动期间只保留最后一次，停手后统一画；页面首次挂载按页序号错开 8ms，最多 160ms，避免一开工程十几张缩略图同时画。
- 绘制降采样：`drawPageThumbnail` 增加 `maxDepth: 3` 与 `minPixelSize: 0.5`。34×22 下更深的嵌套和投影小于半像素的节点不再绘制；页面内容包围盒与画板底色仍然保留。
- 测试：5000 节点场景（50 画板 × 100 子节点，共 5,051 个节点）的缩略图只画 50 个画板，其余 5,001 个节点不进入绘制；mock canvas 平均 **0.37ms/次**。断言在 `src/bench/render.bench.test.ts` 内，不新增假按钮或假路径。
- 边界：0.37ms 是 mock context 的 JS 调用成本，不代表真实 GPU 光栅；缩略图现在不是逐帧实时，而是停手后 100ms 更新，这是为了避免和主画布抢帧。真实窗口还要看拖动时主画布帧时间与缩略图更新体感。

交付指纹（补丁后）：`npm run gate` PASS，16 个测试文件 / 84 条测试；前端 `index-B0_9leUO.js` 347.69 kB；EXE 3,233 KB，2026-11-23 19:01:34。

**WebGPU 的位置**：这轮不接 WebGPU。先把 Canvas 2D 的重复绘制、缓存和缩略图降采样稳定下来；`draw.ts` 仍保持“文档进、绘制出”的纯函数边界，后续 WebGPU 应作为栅格化后端或独立叠加层接入，而不是再造一套场景逻辑。现在加 WebGPU 只会把未稳定的绘制路径复制成两份。

## 2026-11-26 多画板可见区索引

**问题**

5000 节点基准里画板只有 50 个，根循环不算贵；真实设计经常有几百到几千个同级画板。旧路径每帧都把每个根画板交给 `drawNode`，虽然 `intersects` 会跳过视口外内容，但遍历、属性读取与 transforms 仍随画板数量线性增长。

**改法**

- `draw.ts` 新增根级画板空间索引：`FRAME_INDEX_CELL = 512` 场景像素，`FRAME_INDEX_MAX_CELLS = 64` 单画板最多占 64 格，超过的进 `oversized` 列表，避免超大画板把网格撑爆。
- 每帧先按视口 AABB 查询覆盖网格，`FRAME_INDEX_MAX_QUERY_CELLS = 4096` 防御极端缩放；查询结果按原 `children` 顺序排序，保持 z-order 不变。
- 视口外扩 `48 / scale` 屏幕像素，覆盖画板阴影、名称标签与部分选边框。
- 根节点少于 24 个，或根上有蒙版时，直接退回原 `drawChildren`，不在小工程上增加索引开销。
- 索引缓存为 `WeakMap<GromaDoc, Map<rootId, FrameSpatialIndex>>`；每次绘制前计算位置/尺寸/旋转/显隐签名，拖动、缩放、撤销或删除后自动重建，避免只比较 `children` 数组引用导致索引停在旧坐标。
- 旋转画板按四角旋转后的 AABB 入网格，避免旋转后只登记原包围盒而漏画边角。

**实测**

- 600 画板 × 8 子节点，共 5,399 个节点；1420×880 视口、空闲时 30 次平均 **0.14ms**，每帧只绘制 **57 / 5,399** 个节点（4 个可见画板 + 其子节点）。同一轮全量 gate 与 Vexa 编译并行时该值涨到 0.82ms，属于测试机负载波动，不作为 SLA。
- 原有 5000 节点基准仍通过：平均约 1.9ms；34×22 页缩略图 0.34ms。
- 真实 EXE：`Perf-600.groma`（600 画板 / 5,400 图层，1.6 MB scene）100% 缩放只出现视口附近 4 块画板，左栏 600 个画板行可滚动，页面检查器显示“600 个画板”。截图 `shots/many-frames-600.png`。
- 门禁：26 文件 / 173 条测试、MCP selftest、前端构建与 EXE 打包全部通过；EXE 3,301 KB，2026-11-26 07:34:37。
- 同日 C06/C07 补图片裁剪、粘贴与字距后重新 gate：27 文件 / 179 条，CSS 60.35 kB、JS 501.17 kB，EXE 3,301 KB，2026-11-26 13:29:18；本轮没有改根级画板索引或视口裁剪，性能路径未变。
- 同日 C06/C07 再补形状图片填充、粘贴成填充、段落间距、项目符号/数字列表与字体建议后重建：28 文件 / 187 条，CSS 62.07 kB、JS 509.67 kB，EXE 3,384,832 B（3,306 KB），2026-11-26 13:53:00。图片填充只在命中的形状内多一次 clipPath/clip 与 drawImage，列表只在文本分行时加前缀；未改空间索引、视口裁剪和文本缓存路径，5000 节点地基本轮未重跑，性能结论沿用上一轮。
- 同日补多投影/整层模糊与 Shift+2 选中适配后重建：29 文件 / 192 条，CSS 62.54 kB、JS 515.57 kB，EXE 3,386,368 B（3,307 KB），2026-11-26 20:53:28。效果只对有 `effects` 的节点建离屏层，普通节点仍走原路径；离屏层像素密度跟随 DPR/导出倍率并封顶 4096px，避免 6400% 时爆内存。选中适配只改 viewport，不改文档。5000 节点基准未重跑，地基路径不变。

**边界**

- 索引只处理根级画板；画板内部仍按 `drawNode` 的视口裁剪逐层跳过。
- 非裁剪容器的子图层若大量越出自身 `w/h`，候选仍以容器自身外接框为准；这类工程应把容器包住内容，或后续给 Section 单独做子树包围盒。
- 0.14ms 是 mock context 的 JS 调用成本，不等于真实 GPU 光栅与 60fps；真实窗口的平移帧时间仍待 HUD 量化。

## 2026-11-26 百画板总览：缩放快照 + 位图 LOD

**问题**

旧版虽然有根级画板索引，但每次滚轮都提交 zoom 并整场重画。200 画板 × 50 子节点（10,200 图层）在 10% 总览下：每步约 90ms，主线程 58.4ms，rAF p95 56.3ms / max 84.6ms。画板越多越卡，和开源工具“百块画板上限”一致。

**改法**

- **滚轮缩放改成位图快照**：开始缩放时把内容区缓存成一张位图；手势中只按锚点缩放这张图并重画标尺；停手 180ms 后才把最终 viewport 写回 store 并做一次真实矢量重画。点击或落笔前会先提交预览，避免点在旧视口上。
- **总览 LOD**：`scale < 0.5` 时跳过屏幕尺寸小于 4px 的叶子节点；`scale < 0.3` 时不再画几百个画板阴影和名称标签，画板本身与选择框保留。
- **画板缩略图缓存**：`scale < 0.2` 时每块根画板压成一张小图（5% 档位、DPR 上限 2、总量 64MB 封顶），平移/缩放只贴图；缓存键含画板 id 与档位，每张记录建图时整棵子树的对象引用，编辑一块只重建这一块。
- **首次总览分帧补图**：进入百画板总览时每帧只新建 6 张画板小图，其余先用真实画板占位；CanvasView 在 `overviewPending > 0` 时续帧，直到补齐。图片资产异步到位只在这时整批失效。
- **左栏降负载**：画板/区块计数按 `doc` memo；`LayerNode` 加 `memo`，viewport 变化不再重渲染 600 行；`.layer-row` 加 `content-visibility:auto` 与 `contain-intrinsic-size`。

**实测**

- 200 画板 / 10,200 图层，10% 总览，40 次交替滚轮：每步 52.4ms（几乎全是 32ms 采样间隔），主线程 **251.6ms / 40 = 6.3ms/步**，Script **37.6ms / 40 = 0.94ms/步**，rAF **p95 0.8ms / max 3.4ms**；改前 p95 56.3ms。
- 600 画板 / 5,399 图层，7% 总览：30 次滚轮主线程 **246.7ms / 30 = 8.2ms/步**，Script **43.1ms / 30 = 1.4ms/步**，rAF **p95 8.0ms / max 9.0ms**，画面仍显示每块画板里的色块，不是空白矩形。
- 600 画板平移：30 次主线程 **439ms / 30 = 14.6ms/步**，rAF **p95 1.9ms / max 21.4ms**（一次 GC/重绘尖峰，p50 0.9ms）。
- 总览截图 `shots/perf-200-verified.png`、`shots/perf-600-verified.png`；面积与内容均可辨认，左栏 600 行可滚动。

**边界**

- 位图缓存只在 `<20%` 使用；20% 以上仍走真实矢量，避免拖动细小图层时看到旧图。
- 缩略图在总览倍率下不即时反映子图层编辑；停手后只重建被改的那一块，放大到 20% 以上回到真实绘制。
- 缩放预览期间缩放百分比与页面缩略图停在手势前的值，停手后更新；这是用 180ms 延迟换连续帧。
- 这次量化的是 WebView2 真实窗口主线程与 rAF 回调时长，不是 GPU 端到端 60fps 证明；仍缺持续 60 秒采样与选择层分离。
- 构建指纹：CSS 62.60 kB、JS 518.90 kB，EXE 3,387,392 B（3,308 KB），2026-11-26 23:14:27；`npm test` 29 文件 / 193 条、`tsc --noEmit`、Vite build、Tauri build 与 MCP 自检全过。

## 2026-11-26 百画板增量缩略图：编辑一块不再重做 600 张

**问题**

旧缓存只要文档一变，下一次停手就把全部画板小图清空重建。600 画板总览下拖动一块画板，松手瞬间重画 600 张小图；200 画板也一样。这是“超过 100 个画布特别卡”最容易被摸到的卡点。

**改法**

- 缓存从“按画板对象 + 档位”改成 `doc.name + parentId + 画板 id + 档位 + DPR` 的 `Map`，淘汰时能正确减字节，不再靠 `WeakMap` 整批丢失。
- 每张缩略图保存建图时整棵子树（画板 + 所有后代）的对象引用；命中时逐层比对引用。画板移动只换画板对象，子图层编辑只换子对象，都能定位到唯一一块。
- 不匹配才重建；CanvasView 的补图循环沿用上一节，文档变化不会清空其他 599 张。

**实测（同一份工程、同一拖拽脚本、旧 EXE 与 23:14 新 EXE A/B）**

- 200 画板 10%：拖一块画板松手，旧版重建 **200 张**、rAF **p95 77.1ms / max 77.1ms**、1 个 >16ms 长帧；新版只重建 **1 张**、rAF **p95 6.4ms / max 6.4ms**、0 长帧。
- 600 画板 7%：旧版重建 **600 张**、rAF **p95 114.4ms / max 114.4ms**、1 个长帧；新版只重建 **1 张**、rAF **p95 11.3ms / max 11.3ms**、0 长帧。
- 600 画板冷启动后首次 `Shift+1` 总览：600 张分帧补齐，500ms 内先补 79 张，2.6s 内全部完成；rAF **p50 12.2ms / p95 23.0ms / max 29.7ms**，没有 >32ms 长帧。补图期间画板已可见，不是空白等图。
- 截图 `shots/perf-200-drag-after.png`、`shots/perf-600-drag-after.png`、`shots/perf-600-fit-after.png`；左栏仍显示 200 / 600 个画板。
- 复现脚本 `tools/cdp-overview-drag.mjs`（用状态栏世界坐标反算缩放，稳定点中第一块画板并拖 14px）、`tools/cdp-fit-perf.mjs`（首次总览补图与 rAF）、`tools/cdp-set-zoom100.mjs`（先把工程停在 100% 再冷启动测总览）。

**边界**

- 比对的是对象引用，不是像素哈希；从工程外部手改 `scene.json` 后必须重开工程才进入新文档树。
- 文档停手重建一块仍有约 6–14ms；本次只消除“全部重建”，没有把单块缩略图渲染搬到 Worker。
- 这次仍用 rAF 回调时长衡量主线程，不是端到端 GPU 帧率；600 画板连续 60 秒采样与选择层分离仍未做。
