> 这一轮只做“楼底下的混凝土”，不铺新面板。目标不是功能更多，而是：
> **双击能开、编辑不丢、撤销不脏、坏文件不崩、数据规模上来后仍可解释。**

## 二 实测数字（Windows 本机，5000 节点）

| 指标 | 实测 |
| --- | --- |
| 命中：最底层首节点（最坏逆序遍历） | 0.10–0.33ms |
| 命中：最后绘制节点（最好情形） | 0.001–0.003ms |
| 200 步连续撤销 | 0.29–0.55s（单步约 1.5–2.8ms） |
| 2000 节点子树复制 | 4–7ms |
| 全树 `JSON.stringify` | 8–9ms / 1.45MB |
| 全树结构校验 | 约 30ms |
| 100 次「写→读→写」 | 约 13.7s，字节不一致 0 次 |

**边界**：这些是数据层与绘制入口的基准，不是真实画布 60fps 的证明。真实帧率、GPU 栅格化、复杂文字排版仍需单独量；README 0.9 已明确标注“尚未验证”。

## 三 为什么这样能避免 Reelix 式失败

1. **先定不变量，再写 UI**：节点只能通过命令改；结构字段不能从 patch 穿透；坏树在加载时就被拦下。
2. **每个“能用”的路径都有测试**：新增/删除/复制/撤销/保存/加载/保存并发，不是只靠手点一次。
3. **基准是代码，不是话术**：`npm run bench` 可重复跑；README 记录区间，不写“应该很快”。
4. **保存不会倒退**：写前快照、原子写、同工程串行保存；旧异步保存不可能覆盖新内容。
5. **MCP 不绕开地基**：MCP 写盘也走结构校验；复制/删除按真实父子关系处理，不再制造孤儿。

- 版本迁移只有 version 1；`migrate(doc)` 未实现，未知版本直接拒绝。
- 关闭窗口前未做“最后一笔保存”的阻塞式 flush，依赖 600ms 去抖自动保存。
