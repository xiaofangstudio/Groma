**边界**：这些是数据层与绘制入口的基准，不是真实画布 60fps 的证明。真实帧率、GPU 栅格化、复杂文字排版仍需单独量；README 0.9 已明确标注“尚未验证”。

## 三 为什么这样能避免 Reelix 式失败

1. **先定不变量，再写 UI**：节点只能通过命令改；结构字段不能从 patch 穿透；坏树在加载时就被拦下。
2. **每个“能用”的路径都有测试**：新增/删除/复制/撤销/保存/加载/保存并发，不是只靠手点一次。
3. **基准是代码，不是话术**：`npm run bench` 可重复跑；README 记录区间，不写“应该很快”。
4. **保存不会倒退**：写前快照、原子写、同工程串行保存；旧异步保存不可能覆盖新内容。
5. **MCP 不绕开地基**：MCP 写盘也走结构校验；复制/删除按真实父子关系处理，不再制造孤儿。

## 五 快照写入去重（2026-11-23）

版本历史落地后，保存链路暴露出两类“同一内容反复留版本”的噪音：

1. 打开工程初次挂载就自动保存一次 → 凭空多一个快照；
2. 手动存版本时 `saveProject` 自己快照一次 + `createSnapshot` 再快照一次 → 一次点击两个版本；
3. 恢复版本后紧接着的自动保存把同一份恢复内容再记一个版本 → 回滚一次涨两条。

处理：

- `EditorShell` 用 `savedDocRef/savedProjectRef` 守卫：doc 与 projectId 都是初始值就跳过；新工程 id 到位、真实编辑后照常保存。
- Rust `groma_save_project` 增加可选 `snapshot_before`（默认 true）；手动存版本传 false，只落 scene，再由 `groma_create_snapshot` 写一条。
- `VersionHistory` 恢复前先 `saveProject(...,false)`，把内存里尚未等到 600ms 去抖的改动先落盘；否则“恢复前留底”会漏掉刚改的内容。
- Rust 保存前读当前 `scene.json`，与待写文本完全一致时跳过 `snapshot`。恢复后的自动保存、重复保存都是同内容，不再新增版本。
- 快照仍是整份 JSON 副本，最多 20 份；不做压缩和增量，20 份是磁盘保护不是无限历史。

实测（`未命名设计-15.groma`，最终 EXE）：

| 操作 | 快照文件数 |
| --- | --- |
| 打开工程前后 | 13 → 13 |
| 手动“存一个版本” | 9 → 10（仅一条） |
| 恢复最新版 | 12 → 13（只增加恢复前留底） |
| 恢复 13:36:29 的三页快照 | 13 → 14；画布从 1 页回到 3 页 |

边界：这里的“相同”是序列化文本完全一致；若未来引入格式化差异或迁移，语义相同但字节不同仍会留快照。关闭窗口前 600ms 内的最后一笔改动仍靠去抖自动保存，崩溃恢复入口未做。
